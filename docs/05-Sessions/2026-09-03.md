# Session 2026-09-03

Mac dropped six FBX files into `game/assets/characters/astronaut/` — an
authored suited astronaut and four Mixamo animations — and asked which one
works and whether it could go in the game. Both. It is in.

## Changed in the editor (Mac)

- Nothing this session. The FBX set arrived as loose files.

## Changed in code (Claude)

- **Worked out what the six files actually are**, by parsing the FBX binaries
  before importing anything:
  - `Idle_with_skin.fbx` is the only complete one — skin, rig and a clip. It is
    what everything hangs off.
  - The four skinless clips share a **byte-identical 41-bone skeleton in
    identical order** with it, so their tracks resolve against the skinned rig
    with **no retargeting**. Confirmed by loading all three onto it and
    rendering.
  - `astronaut_01_noBackpack.fbx` is the *same* mesh as the one inside
    `Idle_with_skin.fbx` — same geometry name, same 37,235 verts, same bbox —
    with no rig. Kept as the clean master, referenced by nothing.
  - Every clip is **in-place**: the hips translate 0.000 m across all four.
    Right for a velocity-driven controller, and it is why the blend space had
    to be calibrated rather than read off the files.
- **Each clip file now imports as an `AnimationLibrary`**, not a scene, with
  `.import` slices giving the clips their names — `idle`, `walk`, `run`, and
  the jump cut into `jump` / `fall` / `land`. The rig imports with
  `animation/import=false`. Nothing is copied into an authored resource, so a
  re-export cannot leave a stale second copy behind.
- **New `scenes/player/astronaut_rig.tscn` + `scripts/player/astronaut_rig.gd`.**
  An AnimationTree state machine: `Ground` (a 1D locomotion blend into a time
  scale), `Jump`, `Fall`, `Land`. The controller reports speed, grounded and
  vertical velocity and **never names a clip**.
- **`astronaut.tscn`**: the capsule torso, sphere helmet and box pack are gone,
  replaced by the rig under `Body`. Collision capsule 1.8 → 2.0 m to match the
  2.03 m figure — Mac's call, asked and answered.
- **`astronaut.gd`**: one `@onready`, one `_animate()` called after
  `move_and_slide()`, and the AnimationTree switched off while driving.
- **`debug_panel.gd`**: the rig registered in `_discover()`, so its cycle
  speeds and stride scale are on F1. The panel's own note warns that this is
  the step a new system silently misses.
- **New `tests/test_astronaut_rig.tscn`** — clips present and looping the way
  they should, skeleton intact, facing correct, blend landing on the right clip
  at each speed, and every air state reachable and releasing.
- **New `tests/probe_astronaut_clips.tscn`** and a rewritten
  `tests/astronaut_capture.tscn`.
- All 28 tests pass, boot is clean.

## Broke / noticed

- **The model faces +Z; the controller drives -Z.** Caught before it shipped, by
  measuring the rig's own ankle-to-toe vector — (0.18, 0, 0.98) — rather than
  eyeballing a render. Wired naively the astronaut moonwalks, and because that
  reads as *inverted movement*, the tempting fix is to flip the controller's
  `atan2`, which would leave camera-relative movement genuinely backwards. Same
  family as the [[Rover]]'s `ENGINE_FORCE_SIGN`. The 180° correction lives on
  the rig node and is asserted in the test.
- **The clips' natural speeds had to be measured, not assumed.** In-place
  animation carries no speed, but the stride does: two steps to a cycle, widest
  toe separation over cycle length. Walk **2.06 m/s**, run **4.36 m/s** against
  game speeds of 3.2 and 6.4 — 1.55x and 1.47x, near enough the same multiple
  that one `stride_scale` of 1.5 covers both.
- **Low gravity decided the jump's shape.** A 1.9 m jump hangs ~2.1 s against a
  0.4 s airborne phase, so looping the air clip would cycle the legs five times
  and read as flailing. The slices are non-looping and *hold* their last frame
  instead, which reads as floating. The jump's phase boundaries came off the
  feet: takeoff f25, apex f31, touchdown f37 of 65.
- **`advance_mode = ENABLED` means "only via `travel()`."** Condition-driven
  transitions need `AUTO`. Nothing warns — the machine just sits in its start
  state. Cost three failures that looked like a wrong parameter path. Now a
  verified engine fact.
- **`AnimationNodeStartState` cannot be written into a `.tscn`.** Taking the
  whole scene down with it, and through a `preload`, the test script — which
  presented as the documented "a test whose script will not compile runs
  forever". The parse error was at the top of the output, exactly as
  CLAUDE.md says it would be.
- **Piping `--import` into `head` killed Godot partway through** and left a
  `.import` Godot then rewrote with `fbx/importer` flipped to FBX2glTF, which
  is not installed. The failure surfaced as "Failed loading resource" naming
  the *asset*, with nothing about the setting. Both halves are now facts.
- **The suit is untextured** — flat 0.906 grey, roughness 1.0. It reads at mean
  luma 0.26–0.39 under the 5° star, so *not* the black silhouette
  [[The-Planet]]'s lighting note would predict, but it has no material of its
  own. Left alone: look work, unspent by design.
- **The back rack is now visibly proud of the figure.** It sits at z = 0.78 m,
  tuned against a placeholder box that no longer exists; the authored torso's
  back is around z = 0.3, so a carried crate rides ~0.25 m clear. Visible in
  `previews/2026-09-03/astronaut-20_carrying_side.png`. Left for Mac — it is a
  placement judgement, not a bug.
